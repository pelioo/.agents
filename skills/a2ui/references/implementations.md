# A2UI 已知实现状态

A2UI 协议本身**不限前端技术栈**，但"协议理论支持"和"实际有可用渲染器"是两回事。本文档列出截至 2025 年已知的 A2UI 渲染器实现情况，供 Agent / 开发者在选用前参考。

---

## 实现状态总览

| 平台/技术栈 | 状态 | 备注 |
|---|---|---|
| **React Native** | ✅ 已知实现 | 当前主流实现平台，文档中部分示例（如 `non-WebView` 表述）可能源自此生态 |
| **Web (React / Vue / Svelte)** | ⚠️ 理论支持 | 协议不限，但需自行实现 catalog 渲染层或等待官方 Web 渲染器 |
| **Flutter** | ❓ 未确认 | 协议不限，未见公开实现 |
| **Swift UI / Jetpack Compose** | ❓ 未确认 | 协议不限，未见公开实现 |
| **任意 JSON 消费框架** | ⚠️ 可实现 | 只要按 `cteno/v1` schema 解析即可 |

**状态图例**：
- ✅ **已知实现**：有可用的开源/商业 A2UI 渲染器
- ⚠️ **理论支持 / 可实现**：协议不限，需要自行实现或等待官方
- ❓ **未确认**：协议不限，但未见公开实现

---

## 使用建议

1. **确认平台支持**：在选用 A2UI 前，先确认目标客户端已有可用的 A2UI 渲染器
2. **无渲染器时的降级**：客户端不支持 A2UI 时，参考 [SKILL.md 的"已知限制与降级策略"段](../SKILL.md#已知限制与降级策略)，主动降级到 Markdown 输出
3. **本 skill 的作用**：无论目标平台是哪个，只要该平台有 A2UI 渲染器，本 skill 提供的 JSON 生成逻辑（消息类型、组件 ID、dataModel 路径、diff 优化）都通用

---

## 为何不在主文档中强行绑定单一技术栈

A2UI 协议与具体渲染技术栈正交（orthogonal）：
- **协议层**：JSON 形状 + 4 种消息类型 + catalog 命名空间 + `${path}` 数据绑定
- **实现层**：任意能消费 JSON 的 UI 框架（React Native / Web / Flutter / 原生 iOS / Android 等）

把"协议中立"和"实现状态"分两层描述在两份文档中：
- SKILL.md 讲**协议原则**（不限技术栈）
- 本文档讲**现实约束**（哪些平台有渲染器）

避免误导读者认为"某个具体客户端必须用 React Native"。

## 如何贡献新实现状态

如果你知道某个平台已有可用的 A2UI 渲染器，请：

1. 在上表中更新对应行的状态
2. 添加一行说明：链接到仓库/文档/官网
3. 在 SKILL.md 主文档同步更新相关引用（如有）

实现可用性的真实信息比协议文档本身更重要 —— 它决定了 Agent 在该平台上能否真的使用 A2UI。
